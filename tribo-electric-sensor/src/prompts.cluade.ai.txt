    No API key: adsb.lol’s public API is free and needs no registration, so I removed all the key and header handling.
    Endpoint: It calls https://api.adsb.lol/v2/point/{lat}/{lon}/{dist}, with --dist in nautical miles. The response uses the same ac list and now field as ADS-B Exchange, so the parsing and CSV columns are unchanged.
    Output: It writes 10 s windows every 5 s, to adsb_data/adsb_YYYYMMDDTHHMMSS.mmm.csv, in the same format as before. Rows, columns and filenames match the ADS-B Exchange version, so your downstream code won’t need to change.
    Polling rate: It polls every 1 s by default. Public free APIs are shared, so I’d avoid going much faster than that (--poll). The script logs any failed poll and carries on.
    Radius limit: As far as I know, the maximum radius is 250 nm. A larger --dist may return an error.
    Other endpoints: If you want a different adsb.lol endpoint, such as /v2/lat/{lat}/lon/{lon}/dist/{dist}, pass it with --url.

I changed adsb_lol_recorder.py in place so it takes a rectangle instead of a centre and radius. I tested it against a local fake server again, not the real adsb.lol API. With a small box around one of two fake aircraft, only that aircraft appeared in the CSV, and out-of-range or badly ordered boxes were rejected with a clear error.

python adsb_lol_recorder.py --lat-min 40.5 --lat-max 41.5 --lon-min 28.5 --lon-max 29.5

adsb.lol’s public API only supports circle queries (the bounding-box query is feeder-only). The script therefore works in two steps:

    Covering circle: It centres a circle on the rectangle with a radius reaching the farthest corner, plus a 1 nm margin. For the example above that is a circle at (41.0, 29.0) with a 39 nm radius.
    Filtering: After each poll it keeps only aircraft whose position is inside the rectangle. Aircraft with no position are dropped.

The output is unchanged: 10 s windows every 5 s, in the same CSV columns and filenames as before. It prints the circle it chose at startup.

    Size limit: If the rectangle’s covering circle is over 250 nm, the script stops with an error and asks for a smaller rectangle. That limit is only what I believe the public API allows, so raise it with --max-radius if you find otherwise.
    Long thin boxes: A long, thin rectangle is inefficient because the circle covers a lot of area you throw away. A 1° × 6° strip, for example, needs a circle roughly 180 nm in radius, which is well under the limit but returns far more aircraft than you keep.
    Antimeridian: A rectangle can’t cross the ±180° longitude line. It needs lon-min < lon-max, and the script checks this.

Time matching

    Audio time: Each chunk’s start time comes from its bands_*.npy filename (local time). Its label time is the chunk centre, start + 2.5 s.
    ADS-B time: Each position’s true time is t - seen_pos, not the poll time t, so stale repeated positions aren’t treated as fresh. Duplicate rows from the 50% window overlap are removed.
    Interpolation: Each aircraft is linearly interpolated to the chunk-centre time, only if two real position reports bracket that time and are at most --max-gap (10 s) apart. In my synthetic test the interpolated latitude matched the known trajectory to float32 precision.
    Coverage: A chunk is used only if an ADS-B window file covers its centre time. This keeps “no aircraft” distinct from “recorder wasn’t running”.
    Latency: --time-offset shifts the audio clock before the lookup. ADS-B feeds usually lag real time by a second or two, so a small positive value is often right. I can’t calibrate this for you.
    Split: Train and validation are split chronologically with a 10 s gap, because chunks overlap by 50% and a random split would leak audio into validation.

Model and labels

    Model: A 1D CNN takes the (20, 220500) band array. Each band is scaled by its RMS over the training data, so absolute levels are kept.
    Target: The label is up to 10 aircraft × (altitude, lat, lon). Aircraft are sorted nearest-first to a reference point (--ref-lat/--ref-lon, default the mean of all ADS-B positions), and unused slots are 0.
    Output: The network outputs 40 values: the 30 coordinates plus 10 presence logits. The extra logits are my addition, since a zero-padded slot looks like a real aircraft at zero otherwise. The loss on coordinates only counts real aircraft. decode() turns the 40 values back into your 30-number array in real units.

What to expect

    Baseline: Every epoch prints the model’s validation error next to a baseline that ignores the audio. A 0–20 kHz coil is unlikely to pick up aircraft directly, since ADS-B itself is at 1090 MHz. The model may therefore only learn slow patterns like time of day. If it doesn’t beat the baseline on validation, treat the result as noise.
    Data size: Each chunk file is about 17.6 MB. Files are read lazily from disk, but an hour of recording is roughly 25 GB. Record several separate sessions so the validation period isn’t just the tail of one session.
    Timezone: The audio and ADS-B filenames must be from the same machine or timezone, or the matching will be off by hours.
